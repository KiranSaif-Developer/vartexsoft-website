From Zero to Deployed: How We Structure Our Web Dev Course Projects

Ayaan Raza Founder & Lead Instructor
Aug 4, 2026 7 min read

Every cohort, we get some version of the same question in week one: "when do we start building something real?" It's a fair question — most people who sign up for a coding course have already sat through a free YouTube series or two, and what's usually missing isn't information. It's structure.

So before we talk about frameworks or syntax, here's the actual structure every project in our Web Development track is built around — the same one we use internally when we scope client work.

Start With a Brief, Not a Tutorial

Tutorials tell you exactly what to build, in exact order, with the exact code to type. Client work never works that way. You get a brief: a page count, a rough audience, a handful of "must-haves," and a deadline. Everything else is your call.

That's why every project we assign starts as a one-page brief, not a spec sheet. Students have to make the same calls a freelancer makes on day one — what pages actually matter, what "responsive" means for this specific audience, and where to spend their limited time.

"The gap between a tutorial project and a portfolio project isn't difficulty. It's ambiguity."

— Ayaan Raza, Founder & Lead Instructor

The Four-Stage Structure

Every project — whether it's a landing page in week two or the final capstone — moves through the same four stages. It's deliberately close to how we run actual client engagements.

1. Scope & Wireframe

Before any code gets written, students sketch the page structure and list out the sections they'll need. This step alone eliminates most of the "I don't know where to start" paralysis we used to see constantly.

2. Build in Layers

Structure first (semantic HTML), then layout (CSS Grid/Flexbox), then interactivity (JavaScript or React). Building in layers means a student always has something visible on screen, even if it's unstyled — which keeps momentum up.

3. Mentor Review

Every project gets a real code review from a mentor, not just a pass/fail grade. This is usually where the most learning happens — seeing how a small refactor makes a component reusable, or why a particular naming convention matters six files later.

4. Ship It

The project isn't done until it's deployed and live at a real URL. A finished project sitting in a local folder doesn't go on a portfolio, and it doesn't teach you anything about the parts of web development that happen after "it works on my machine."

What This Actually Fixes

A few things change once projects are structured this way instead of as guided tutorials:

  • Students make real decisions instead of following steps, which is the actual skill that gets tested in interviews.
  • Portfolios end up with genuinely different projects instead of eleven identical to-do apps.
  • Mentor feedback has something specific to respond to, instead of just checking boxes against a spec.
  • Students leave comfortable with ambiguity, which is most of what junior developer work actually is.

Where It Goes From Here

This structure isn't fixed forever — it gets reshaped every few months based on what's actually coming up on client projects. If we notice ourselves leaning on a particular pattern or tool at work, it usually shows up in the course within a term or two. That feedback loop is the whole point of being taught by people still doing the work, not just teaching it.
